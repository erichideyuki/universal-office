## 6. Module state and where it lives in `WriteCtx`

None. The TS modules have only immutable constants (`SETTINGS_AFTER_NOTES`, `NOTE_STYLES`, `NOTE_REF_TEXT`,
`BEFORE_*`, `HYPH_ORDER`, `HF_NS`, `SEP_PPR`, `NOTES_NS`, `REL`, `CT`); they are Rust `const` items. These
functions work on a `Package` (or a string) passed in and are called by the session's save and the D2b
commands, not by `write_document`, so nothing is added to `WriteCtx`. `new_note_paragraphs` takes the
`IdAlloc` explicitly. `page_number_group_ids` takes the store's `parts` because the Rust `wrap_open` is a
`SrcText` that resolves against them.

## 8. Evaluation order around `revisionAttrs` / `mediaRelId` / `linkRelId`

None of the three is used here. The orders that matter and are kept:

- `ensureNoteParts` (notes.ts:64–86): per kind, in order, the part, then the relationship, then the content type;
  `rels` and `ct` are held as local strings and set on the package once at the end (`if (changed)`), the
  settings last. The relationship id is the smallest free `rIdN` of the text as it is at that point (the
  footnote relationship already added when the endnote's id is chosen).
- `patchSettingsNotes`: `footnote` is patched first, and `endnote` sees its result (the footnote element is
  inserted before an existing endnote one).
- `copyHfPartXml` (hf-ops.ts:226): `newId()` is called once per `wp:docPr` that has an `id`, left to right, before
  the paragraph/drawing ids are stripped: the facet's counter (101, 102, …) makes the call order and count visible.
- `dropUnusedHfParts` (hf-ops.ts:241–257): the TS interleaves, per matching relationship, the text cuts with
  `pkg.removePart`; Rust cuts all the text first (`drop_hf_text`) and removes the parts after. No step reads
  the package between them, so the result is the same (the facet compares the final part order and bytes).
  The tags to drop are collected from the ORIGINAL text, each removed by its first occurrence in the current text.
- `writeHyphenationSettings` (settings-xml.ts:82–97): the four elements are handled one after another, each
  insertion point computed from the text as the previous step left it (re-parsed each time).

## 9. Deviations (Opus check first)

| # | Deviation | Why |
|---|---|---|
| W4-1 | `patchSettingsNotes`'s `props` object is `NotePropsArg` (`Unchanged` = key absent / `undefined`, `Remove` = `null`, `Set`); `HyphenationSettings.zone` is an `Option<f64>`; `copy_hf_part_xml` takes `&mut dyn FnMut() -> f64`; `hf_part_xml(kind: &str)` gives `w:hdr` for `"header"` and `w:ftr` for anything else | typed input of the D2 commands; the facet's arguments map onto it one to one |
| W4-2 | `has_note_relationship` keeps the wildcard dots of the TS pattern (they match any one unit), `val_pattern_test` keeps `.` and `+` of the number text as regex syntax | faithful to the TS, which builds regex source from a constant with unescaped dots and from `String(number)` |
| W4-3 | **`remove_override` takes the part path as a literal; the TS builds a `RegExp` and escapes only `.`.** Any other regex character in a path (`+`, `(`, `[`, `$`, …) is syntax in the TS (a stale `Override` stays, or a `SyntaxError` for an unbalanced `[`/`(`), a literal in Rust (the override is removed). The paths come from a relationship `Target`; the corpus has none with such characters, the capture and the V8 rows use only letters, digits and `._/-` (the regex row filters its paths the same way) | dynamic patterns with values as literals (W-D5, G9). Rust's result is the intended one. **Decided (Opus orchestrator, 2026-11-05): keep the literal.** It is the approved rule G9/W-D5 (a dynamic pattern's values are matched as literals); reproducing the TS would mean a save that throws `SyntaxError` or keeps a stale `Override` for a part it just dropped. Listed for the milestone-2 gate with the other G9 sites |
| W4-4 | `free_rid_number` scans the existing ids once instead of searching for each `n` | linear time (the TS is quadratic with many relationships); same result as the substring test, including the leading-zero and over-long id cases |
| W4-5 | `page_number_group_ids` is iterative and returns an `IndexSet<NumKey>`; it needs the store's `parts` to read `wrap_open` | no recursion (item 5); the model's `SrcText` is a reference into the store |
| W4-6 | `settings_part`: a settings relationship whose target the OPC rule resolves to no part counts as "no part" and the write goes to `word/settings.xml` | uo-opc D6 (target resolution), accepted by name there |
| W4-7 | A settings part nested deeper than the parser limit makes the four writers return `Err`; the TS `parseXml` has its own bound | limits for untrusted input (M1 test with 1,500 levels) |
| W4-8 | `note_ref_run` / `new_note_paragraphs` build model values with ids and edit marks: the paragraph takes `ids.para()` and is `mark`ed `props` and `runs`; the TS returns plain objects | the Rust model carries identity and dirty marks (A2/A3). **No parity facet**; M1 only |
| W4-9 | `ensure_note_parts` and the other package writers propagate `Err` for a part the package cannot decode within the limits | uo-opc limits; the TS cannot fail there |
| W4-10 | `NOTE_STYLES` is two `const` structs with a `note_styles(kind)` lookup (`None` for a kind other than footnote/endnote) | typed lookup instead of a `Record` |

No deviation changes a result on the facet's inputs. W4-3 is the one with a visible difference and wants an
Opus decision; W4-8 is outside the parity facet.
